# Documentation Benchmarking

本文件保存 peach-cloud 文档工程已经形成的成熟项目基准，目标是复用信息架构，而不是在每次写 README 时重新搜索外部项目。

## 默认基准

日常文档优先复用以下成熟项目常见做法：

- Spring 系列：入口文档简洁，完整配置/API 行为下沉到 Reference；示例围绕最短成功路径组织。
- Apache Dubbo 等大型中间件：先说明定位和架构，再提供 Getting Started、核心能力和深入文档导航。
- Redisson 等基础设施库：Quick Start、常用 API、配置入口与完整文档链接优先，避免首页承载全部实现细节。
- Kubernetes / OpenTelemetry 等复杂系统：概念、任务型 How-to、Reference、架构解释分离，避免一个文档同时承担所有读者目标。

这些基准只用于决定“信息应该如何组织、读者路径如何设计、哪些内容应拆分”，不得复制其文案，也不得据此推断 peach-cloud 已实现的功能。

## 什么时候不重新调研

以下任务直接使用本 Skill 已沉淀的 reference，不额外查询成熟项目：

- 普通 README 新增或小幅重构。
- 配置/API/Quickstart 变化后的同步更新。
- 已有文档的纠错、补图、双语同步和排障补充。
- 同类 Starter 家族的重复文档工作。

## 什么时候允许重新调研

只有出现以下情况之一，才补充新的外部基准：

1. 首次建立一种此前没有覆盖的文档类型或信息架构。
2. 新增复杂基础设施/平台级模块，现有基准无法解释其读者路径。
3. 用户明确要求对标某个成熟项目或行业方案。
4. 现有 reference 与当前主流官方文档实践明显冲突或已经过时。
5. 团队准备修改文档工程规范本身，而不是仅编写某个模块文档。

重新调研时优先 2~4 个成熟项目的官方仓库或官方文档，提炼结构、导航、示例组织和维护机制；完成后把稳定结论回写到本 reference，后续任务复用，不重复消耗上下文。

## Benchmark Output

外部对标只产生三类可复用结论：

- `Keep`：适合 peach-cloud，写入稳定规范。
- `Adapt`：思路可用，但必须结合 peach-cloud 模块边界调整。
- `Reject`：不适合当前项目，记录原因，避免后续反复讨论。

对标结论不能覆盖 Source of Truth。任何类名、配置 key、默认值、模块关系、运行语义和支持状态仍必须由当前源码证据确认。

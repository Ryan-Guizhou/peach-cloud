# 控制台路由与首次初始化

## 页面与权限

管理页面使用浅色 AdminLayout；认证页共用 AuthShell。注册和找回密码尚未接入业务接口，只显示未开放说明。

`src/router/dynamic.ts` 的本地目录覆盖已实现业务页面；实际业务路由和菜单来自登录权限快照。工作台与个人中心是登录后的基础入口。空授权不回退显示整套业务菜单，前端不通过管理员角色名绕过权限。

已知内置 URL 使用明确组件映射；其他路径必须匹配本地业务组件白名单。业务编码不用于猜测组件。后端有菜单但没有对应有效路由，或缺少该页面所需查看权限时，不生成不可访问的菜单项。

## 首次初始化与缓存

项目尚未上线，数据库使用首个完整版本 V1。首次启动应连接全新空 schema，由 V1 完成建表、系统种子数据、四类业务编码及规则账本、菜单路由绑定和管理员授权初始化。V12/V13/V14/V15 是开发期间曾采用的增量方案，不再作为默认启动迁移链或操作步骤。

首次初始化后的菜单、功能、路由、角色分别采用 M0001、F0001、RT0001、RL0001 格式，功能父级、菜单/路由/资源所属功能、角色绑定及授权引用使用对应的真实业务编码。前端直接展示后端值，不进行显示层补零或前缀转换。资源权限标识和业务 URL 保持其接口约定。

已有菜单不代表已有接口权限。V1 同时初始化已实现页面的按钮权限、按实际 Controller 方法和路径定义的 API 资源，以及系统管理员资源授权。文件记录、存储实例和对象浏览分别需要 `fileRecord:view`、`storageInstance:view`、`objectBrowser:view`；路由列表请求需要 API 资源 `POST:/api/auth/router/pageList`。普通角色继续按实际授权访问，网关鉴权保持启用。

已有 V14 等开发数据库不能直接套用新的 V1，也不提供 clean、repair 或自动兼容接管。请使用新的空 schema；若需要重建旧开发库，应由使用者先明确备份和重建范围，再自行处理原有数据。本次前端调整不执行旧库清理或覆盖。

菜单、功能、路由、角色由后端 `CodeGenerator.next` 按 MENU、FUNCTION、ROUTER、ROLE 稳定业务类型发号，对应前缀 M、F、RT、RL；数字固定四位，最大 9999，耗尽拒绝发号。客户端不填写新编码，已有编码只读。V1 初始化种子租户的规则和账本；以后创建的新租户仍需配置四类规则。缺少规则时发号失败，不自动猜测规则。

应用连接新的初始化数据库后应退出并重新登录，获取当前数据库的权限快照；直接刷新仍可能读取旧浏览器登录缓存。初始化失败会阻止应用启动，应检查并解决具体错误，不通过跳过校验继续运行。

## 验证

前端目录执行 `npm.cmd test` 和 `npm.cmd run build`。`python scripts/login-audit-smoke.py` 使用本地接口夹具与 Chrome 验证文件管理、存储实例、对象浏览入口及空态，以及工作台、登录日志、刷新、查询与失败恢复、详情、窄屏、退出、认证页面和加密登录返回；需要 websocket-client 和 cryptography。

接口夹具不能证明实际数据库已初始化或账号已获得授权。实际环境应在 V1 初始化成功后重新登录，检查各菜单对应页面和后端接口权限。数据库初始化回归位于 `peach-database` 的 `PeachDatabaseMigrationTest`；路由发号回归位于 `peach-auth-launch` 的 `RouterCodeTest`。

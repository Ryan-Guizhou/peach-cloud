# 菜单、功能、路由和角色编码实施约定

> **数据库方案已替代 — 2026-11-24：** 用户确认项目未上线，改用全新空 schema 的首个完整 V1，一次初始化 schema、seed、四类真实编码和权限。本文关于历史增量迁移、旧新映射和冻结旧迁移链的内容保留为历史决定，不再是当前待执行方案。旧 V14 开发库不能直接应用新 V1 或通过 clean/repair 自动兼容；应使用新 schema，或由使用者先明确备份和重建范围。四类编码格式、前端只读及资源权限标识不改的约定继续有效。

历史状态：用户曾要求继续实施现有编码调整。独立的 setting 查询 SQL 属性错误已修复。

## Goal

菜单使用 M0001、功能使用 F0001、路由使用 RT0001、角色使用 RL0001。统一使用现有 CodeGenerator 与 MySQL 发号账本，不允许客户端自行指定新编码。

## Scope

- 四类新增、编辑、列表和前端表单；创建时自动发号，编码创建后只读。
- 迁移现有不符合格式的四类业务编码；已有符合格式的编码保留。
- 同步功能父子关系、菜单和路由功能归属、资源功能归属、角色用户绑定、功能授权和资源授权等现有引用，保留映射证据。
- 修复菜单新增硬编码租户和应用为 111 的错误，按当前可信会话与管理应用保存。

## Non-goals

本次不调整资源编码与鉴权字段，不实现资源业务流水号，不改变实际资源权限、角色权限或业务 URL，不调整主键 ID。

## Compatibility

菜单名、功能名、角色名、ID 与页面 URL 保留；资源中 user:view、POST:/api/... 等权限标识不变。旧浏览器/Redis 权限快照不得在编码迁移后继续使用，升级后重新登录。外部调用方持有旧业务编码的，需要按迁移映射更新，不能假定旧编码仍可直接作为新业务编码提交。

## Constraints

- MENU=M、FUNCTION=F、ROUTER=RT、ROLE=RL；数字部分固定四位，从 0001 开始。
- 现有发号器按租户与业务类型隔离，并共享账本冲突保护；序号耗尽至 9999 后受控失败，不回绕、不自动扩位。
- 不改已执行的 Flyway 历史与冻结基线。普通用户的授权边界、租户/应用/机构/年度上下文保持一致。

## Migration

新增向前迁移，先校验既有编码、引用关系和容量，建立旧新编码映射，再同步替换所有引用并校准规则水位和账本。异常引用、冲突或容量不足必须阻止迁移，不静默丢授权。升级期间暂停授权与主数据写入，成功后重新登录。

## Verification

- 自动生成、编码只读、租户隔离、四位格式与序号耗尽的回归测试。
- 真实隔离 MySQL 的历史数据迁移测试，验证功能树、角色绑定、授权、页面 URL、ID 和资源权限标识不丢失。
- 前端测试、类型检查、生产构建及浏览器菜单/权限流程。
- node scripts/verify-changes.mjs。

## Risks

此次迁移会改变对外可见业务编码；旧编码的外部引用与缓存需要更新。资源权限字段保持不变，但其功能、角色外键引用必须完整替换；迁移失败时不得允许新旧代码并行写入。
